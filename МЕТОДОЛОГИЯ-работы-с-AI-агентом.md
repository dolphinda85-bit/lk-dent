# Методология работы с AI-агентом

Как настроить проект так, чтобы AI-агент (Claude Code, Codex и любой совместимый) работал системно: помнил контекст между сессиями, знал ваш проект и действовал по понятным правилам, а не заново угадывал каждый раз.

Руководство самодостаточное - принципы, порядок настройки и готовые шаблоны в приложениях. Подходит и для Claude Code, и для Codex (разница только в именах файлов, см. таблицу в конце).

---

## Зачем это нужно

По умолчанию агент каждую новую сессию начинает с чистого листа: не знает, что за проект, какие правила, что делали вчера. Он придумывает подход заново - и часто мимо.

Методология закрывает четыре дыры:
1. Агент не знает, кто вы - заводим профиль владельца (папка `User/`).
2. Агент не знает проект - заводим базу знаний о проекте.
3. Агент не помнит прошлое - память держим в файлах, а не в переписке.
4. Агент каждый раз работает по-разному - правила пишем один раз.

Итог: агент ведёт себя как обученный сотрудник, а не как случайный подрядчик.

---

## Роли файлов

Всё в проекте делится на роли. Держите их раздельно:

| Роль | Где живёт | Что это | Простыми словами |
|---|---|---|---|
| **Правила** | `CLAUDE.md` / `AGENTS.md` | Как агент работает; точка входа, читается сам | Инструкция сотрудника |
| **Вы** | `User/` | Кто владелец: принципы, экспертиза, голос; один на все проекты | ИИ-клон / аватар |
| **Знания** | `.business/` | Зачем делаем проект: продукты, аудитория, цели, цены | База знаний |
| **Память** | `plans/`, `retrospectives/`, снимок состояния | Что сделали и что дальше | Рабочий журнал |

Порядок не случаен: сначала **кто** думает (`User/`), потом **о чём** (`.business/`). Плюс библиотека `prompts/` - заготовки под типовые задачи.

## Структура проекта

```
проект/
├── CLAUDE.md / AGENTS.md     ← правила для агента
├── User/                     ← кто владелец: принципы, экспертиза, голос (один на все проекты)
├── .business/                ← база знаний о проекте
├── plans/                    ← планы (один план = одна задача)
├── retrospectives/           ← разбор после каждой сессии
├── prompts/                  ← библиотека заготовок
├── templates/                ← образцы файлов
└── scripts/                  ← бэкап, проверки
```

## Правила (файл `CLAUDE.md` / `AGENTS.md`)

Инструкция агента. Держите её **короткой (до 200 строк)** - иначе агент тонет в тексте и жжёт лишние токены.

Что должно быть внутри:
- проект одной строкой;
- структура папок + таблица «что где искать»;
- на чём сделано (стек);
- принципы работы;
- безопасность;
- язык общения.

**Рабочий набор принципов:**
1. Перед задачей о бизнесе - сначала читай базу знаний (`.business/INDEX.md`).
2. Один чат - одна задача. Разные задачи в разных чатах.
3. Прежде чем сочинять промпт с нуля - проверь библиотеку `prompts/`.
4. Большая задача - отдельный план `plans/ГГГГ-ММ-ДД-название.md` с чекбоксами фаз и итогом.
5. В конце сессии - короткая ретроспектива.
6. Перед публикацией/деплоем - проверяй фактически (сборка, логи), не «должно работать».
7. Коммить свои изменения поимённо, без `git add .` вслепую.
8. Необратимое и «наружу» (деплой, удаление, отправка данных) - сначала показать план, потом делать.

Готовый шаблон - приложение А.

## Профиль владельца (`User/`)

Кто вы - отдельно от бизнеса. Принципы, экспертиза, стиль, голос. С ним агент пишет и решает **как вы**, а не «в среднем по интернету». Это «ИИ-клон»: **один профиль на все ваши проекты** - каждый цепляется к нему через свой `CLAUDE.md`.

Разумная разбивка:
```
User/
├── INDEX.md          ← оглавление
├── кто-я.md          ← кто вы, чем занимаетесь
├── принципы.md       ← как с вами работать, ценности
├── экспертиза.md     ← в чём разбираетесь
└── голос.md          ← стиль речи, стоп-слова (или ссылка на скилл голоса)
```

Правило: сначала «кто» (`User/`), потом «о чём» (`.business/`). Не путать с аватаром **клиента** (`.business/audience/`) - тот про то, кому вы продаёте. Заполняется на онбординге, как и база знаний.

---

## База знаний о проекте (`.business/`)

Знания о бизнесе. Агент читает **`INDEX.md` первым**, а дальше - только нужный файл. Это экономит контекст: не грузим всё сразу.

Разумная разбивка:
```
.business/
├── INDEX.md          ← оглавление «надо X → файл Y»
├── company/          ← кто вы, формат, ценности
├── products/         ← что продаёте и по какой цене
├── audience/         ← кто клиенты, их возражения, путь
├── goals/            ← цели: год / квартал / месяц, метрики
├── economics/        ← экономика: выручка, расходы, прогноз
├── marketing/        ← каналы, воронка, конкуренты
├── assets/           ← гайдлайны бренда, отзывы
└── execution/        ← операционка: неделя, бэклог, снимок состояния
```

Заполняется через интервью: агент задаёт вопросы по одному, с вариантами. После блока о продуктах полезно попросить агента назвать 2-3 риска - чтобы не строить воздушный замок на старте.

---

## Память между сессиями

Переписка не сохраняется. Значит, память - в файлах.

**Планы (`plans/`).** Один план = одна задача. Имя `ГГГГ-ММ-ДД-название.md`. Внутри: цель, контекст, фазы с чекбоксами, критерии готовности, риски, открытые вопросы, итог. Обновлять после каждой сессии. Шаблон - приложение Б.

**Ретроспективы (`retrospectives/`).** Короткая заметка на пять пунктов, читается за полминуты: что делали / как решали / решили ли / что улучшить / было-стало. Смысл - передать опыт следующей сессии. Шаблон - приложение В.

**Снимок состояния (`СОСТОЯНИЕ-ПРОЕКТА.md`).** Один файл «где мы сейчас»: текущий фокус, что готово, что дальше, что подвешено.
- Начало сессии: агент читает его первым.
- Конец сессии: обновляет одной-двумя строками.

Это делает переход между сессиями бесшовным - новый чат сразу в контексте.

---

## Библиотека заготовок (`prompts/`)

Готовые промпты под типовые задачи, чтобы не изобретать каждый раз. Правило: **прежде чем писать с нуля - загляни в оглавление**. Разумные разделы: настройка среды, вывод в продакшн (репозиторий, деплой, платежи), приёмы (проверка плана, стресс-тест, планирование недели).

---

## Два приёма, которые ловят проблемы заранее

### Проверка плана свежим взглядом

Агент в том же чате не видит свою работу со стороны. Приём: написал план - открой **новый чат** и попроси разобрать его с трёх сторон (техника, бизнес, удобство для пользователя), можно параллельными субагентами. Свежий взгляд ловит большую часть проблем ещё до реализации. Разбор отчёта: обосновано - правь; мимо - пропусти; новый вопрос - в «Открытые вопросы».

### Стресс-тест «что пойдёт не так» (pre-mortem)

Известный метод принятия решений (pre-mortem): перед крупным шагом представить, что всё уже провалилось, и назвать причины - заранее, а не по факту. Применять перед деплоем на прод, запуском продаж, важным эфиром, релизом.

Рабочая формулировка запроса:
```
Контекст: [что готово - правила, база знаний, лендинг, план, оффер].
Завтра я [делаю что-то важное: запускаю продажи / деплою / провожу демо].

Представь, что это уже провалилось. Назови 10 конкретных причин провала:
- где в главном документе двусмысленности, которые агент поймёт неправильно
- где в базе знаний пробелы, из-за которых решения придётся выдумывать
- где логика противоречит сама себе
- где стек или принципы расходятся с реальностью
- где я переоцениваю объём работы
- где риск заложен, а подстраховки нет
- где пользователь застрянет и уйдёт
- где может упасть прод
- где не продумана безопасность и приватность
- где нет следующего шага после запуска

Критикуй жёстко. В конце - список правок: что и в каком файле исправить.
```
Дальше: внести согласованные правки, записать находки в ретроспективу, через день перечитать свежим взглядом.

## Настройка среды

**Звуковые сигналы.** Чтобы не сидеть над экраном, пока агент работает: звук по завершении задачи и по запросу разрешения. Кросс-платформенно (Mac / Windows / запасной вариант). Образец - приложение Г.

**Защита от опасных команд.** Список запретов, чтобы агент не снёс лишнего и не слил секреты: массовое удаление, связки «выгрузить переменные + отправить наружу», чтение файлов с секретами, слишком широкие права доступа. Образец - приложение Г.

**Голосовой ввод и быстрые скриншоты.** Диктовать быстрее, чем печатать. Скриншот сразу в буфер: Mac `Cmd+Shift+Ctrl+4`, Windows `Win+Shift+S`.

**Секреты - только в системном хранилище (Keychain) или переменных сервера, никогда в репозитории.** Файлы с секретами целиком не читать - только конкретную строку через `grep`.

## Бэкапы

**Приватный репозиторий - единственный источник правды.** С ним синхронизируются все машины.

Продвинутый вариант (мы им пользуемся): **автосинхронизация каждые 15 минут** по циклу «сохранить - подтянуть - отправить». На рабочей машине - через планировщик, на сервере - через расписание. Скрипт объясняет причину сбоя человеческим языком (конфликт правок / нет доступа / нет сети).

Важное правило при работе с двух машин в один репозиторий: не параллельно (то одна, то другая), иначе временная развилка. Начинай с «подтянуть», заканчивай «отправить».

Для старта достаточно ручного бэкапа (кнопка или `git push` в конце сессии). Автосинхронизацию подключать, когда проект вырастет.

## Голос бренда

Если агент пишет тексты от вашего лица (посты, рассылки, статьи, лендинги) - у него должен быть **ваш голос**, а не усреднённый машинный. Полезно вынести это отдельно: паспорт голоса (примеры фраз, регистр, юмор) и список слов-маркеров, которые выдают робота.

Базовые правила, которые стоит задать сразу:
- дефис, не длинное тире - везде;
- избегать канцелярских и «слишком гладких» формулировок;
- меньше натужной разговорности - фальшивое панибратство читается сразу;
- ирония - на явления, не на читателя.

## Один агент или два: Claude Code и Codex вместе

Не нужно дублировать папки. Держите одни проекты, а разным агентам - свои имена файла правил, указывающие на одно содержимое.

**Правила - один файл под двумя именами.** В каждом проекте `CLAUDE.md` - настоящий файл, а `AGENTS.md` - ссылка (симлинк) на него. Оба агента читают одно и то же. Нюанс: если агент сохраняет файл «атомарной заменой», ссылка может порваться - тогда либо правьте правила через основной файл, либо добавьте в бэкап-скрипт шаг, который каждые 15 минут восстанавливает зеркало.

**Скиллы - общие.** Формат `SKILL.md` переносим между агентами. Достаточно, чтобы папка скиллов одного агента ссылалась на папку другого - один набор навыков на обоих.

**Автономность Codex.** Чтобы Codex не спрашивал разрешение на каждый шаг, в `~/.codex/config.toml`:
```toml
approval_policy = "on-request"     # спрашивает только по необходимости
sandbox_mode = "workspace-write"   # сам читает и правит файлы в папке проекта
```
Полный обход (`never` + `danger-full-access`) - только для изолированной папки, рискованно.

### Таблица соответствий

| Что | Claude Code | Codex |
|---|---|---|
| Файл правил | `CLAUDE.md` | `AGENTS.md` |
| Настройки / хуки | `.claude/settings.json` | `~/.codex/config.toml` |
| Автономность | Bypass Permissions | `approval_policy` + `sandbox_mode` |
| Навыки | `~/.claude/skills/` | `~/.codex/skills/` (общий формат `SKILL.md`) |
| Субагенты | параллельные агенты | субагенты (explorer / worker) |

## Чек-лист запуска проекта с нуля

1. Создай структуру папок (`User/`, `.business/`, `plans/`, `retrospectives/`, `prompts/`, `templates/`).
2. Заполни профиль владельца `User/` (кто вы, принципы, экспертиза, голос) - сначала «кто», потом «о чём».
3. Заполни базу знаний через интервью с агентом.
4. Сгенерируй файл правил из шаблона (приложение А).
5. Настрой звуковые сигналы и запреты безопасности (приложение Г).
6. Для Codex - включи автономность в `config.toml`.
7. Первый коммит в приватный репозиторий.
8. Проверь полный цикл на микрозадаче: правила → план → выполнение → отметка готовности → ретро.
